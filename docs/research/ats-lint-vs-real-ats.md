# `ats_lint.py` vs. real ATS / recruiter screening

Research date: 2026-07-16. Scope: compare the heuristic in `src/apply/ats.py` (substring keyword-coverage scoring of a markdown CV draft against a JD, plus a quantified-metrics count and word count) against how Greenhouse, Lever, Workday Recruiting, and Teamtailor actually ingest resumes and how recruiters actually screen, using vendor-primary sources where they exist and clearly-flagged secondary/anecdotal sources where they don't.

## 1. Verdict

`ats_lint.py`'s approach holds up as a **useful pre-submission sanity check for the author's own copy**, but it is **not a proxy for "will this pass an ATS"** — because for three of the four platforms researched (Greenhouse, Lever, Teamtailor), and increasingly for Workday too, there is no such thing as a single opaque keyword-scoring gate to "pass." These are recruiter workflow/tracking tools, not Jobscan-style scoring engines; the closest thing they have to automated ranking is either a Boolean/full-text search a human recruiter chooses to run, or (in 2025-2026) an opt-in AI match/screening layer (Greenhouse Talent Matching, Lever AI Screening by VONQ, Workday HiredScore/Illuminate) that explicitly does *not* auto-reject and is described by its own vendors as going beyond flat keyword matching. **The single biggest gap** is that `ats_lint.py` never touches the artifact that actually gets ingested by any of these systems: it scores the author's markdown source, not the exported PDF/DOCX the CV pipeline produces — so it is structurally blind to the #1 documented cause of real parsing failure (format/layout: columns, tables, headers/footers, images, non-standard fonts), which every vendor that publishes parsing guidance (Greenhouse) explicitly warns about and the tool cannot warn about at all, by construction.

## 2. Platform findings

### Greenhouse

- **Formats accepted / parsing behavior (primary):** Greenhouse Recruiting "scans an imported resume and auto-fills appropriate fields with information it detects" and accepts DOC, DOCX, PDF, TXT, and RTF uploads. Files over 2.5MB will not parse. (Greenhouse Support, "Supported formats for resumes, cover letters and other candidate uploads," https://support.greenhouse.io/hc/en-us/articles/360052218132-Supported-formats-for-resumes-cover-letters-and-other-candidate-uploads)
- **Documented parsing failure causes (primary):** Greenhouse's own troubleshooting article lists, as causes of "unsuccessful resume parse": resumes with spaces between letters, resumes that include graphics/photos/word art, resumes uploaded as an image, and complex layouts (tables, headers/footers, multi-column formatting) — plus a fake-data detector that flags placeholder content like "First Last" or "Company 1." (Greenhouse Support, "Unsuccessful resume parse," https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse)
- **Which fields get extracted:** The support docs confirm auto-fill of candidate profile fields but the exact field list (beyond contact info) isn't itemized in the public help articles; the Harvest API's attachment object only exposes `filename`, `url`, `type`, `content_type` for the resume file itself, not parsed sub-fields — the structured parse result lives inside Greenhouse's own UI, not the public API. (Greenhouse Developer Docs, Harvest API, https://developers.greenhouse.io/harvest.html)
- **Keyword search / ranking for recruiters (primary):** Greenhouse Recruiting has a recruiter-facing full-text Boolean search over candidates ("All Candidates" → toggle "Full Text Search"). It supports AND / OR / NOT, phrase search in quotes, parenthetical grouping, and wildcard stemming (e.g. `Java*` matches "Java" and "JavaScript"), and explicitly searches across resumes, notes, and scorecards together — this is a human-initiated search, not an automatic gate applied to every applicant. (Greenhouse Support, "Search candidates using Boolean queries," https://support.greenhouse.io/hc/en-us/articles/202360199-Search-candidates-using-Boolean-queries; "Search resumes for keywords," https://support.greenhouse.io/hc/en-us/articles/115004600186-Search-resumes-for-keywords)
- **AI matching (primary, new in 2025-2026):** Greenhouse's "Talent Matching" feature uses recruiter-defined, weighted calibration criteria and AI to sort candidates into categories (Strong / Good / Partial / Limited / Needs manual review) based on resume + application-question content, and shows "matched and similar keywords" (i.e., beyond exact substring — it claims conceptual similarity, not just literal string match). Greenhouse states explicitly: "It does not automatically advance or reject candidates. Recruiters and hiring managers remain responsible for all hiring decisions." (Greenhouse Support, "Talent Matching," https://support.greenhouse.io/hc/en-us/articles/41396009937307-Talent-Matching)
- **Parsing engine/partner:** Not disclosed in any primary source found. Third-party blogs claim Sovren "in older Greenhouse support documentation," but this could not be independently verified in current Greenhouse docs — **treat as unverified, flag accordingly.**

### Lever

- **Parsing engine:** Not documented in Lever's own current, publicly reachable help content (the specific article, "Understanding Resume Parsing," is behind a JS-rendered help widget that returned only a client-side error on fetch — content not independently verifiable here). The claim that Lever uses Sovren, sending resumes to hosted Sovren instances to extract contact info, work history, and education, comes from a Quora answer attributed to "a developer who worked on Lever's resume parsing feature." **This is anecdotal/secondary, not a vendor-confirmed primary source** — treat as plausible but unverified. (Quora, "What service does Lever (company) use to parse and extract resume details?," https://www.quora.com/What-service-does-Lever-company-use-to-parse-and-extract-resume-details)
- **API (primary):** Lever's developer docs confirm resumes are handled as binary file attachments via a dedicated resumes endpoint (superseding a deprecated inline `resume` field), and that candidate/application data lives under `/opportunities/` (the `/candidates/` path was deprecated in 2020). No public API surface exposes a "match score" or parsed keyword list. (Lever Developer Documentation, https://hire.lever.co/developer/documentation)
- **AI screening (primary, new in 2026):** Lever's Spring 2026 release added "AI Screening by VONQ" — every applicant goes through a structured screening interaction at time of application, producing a "Candidate Dossier" (structured summary, screening insights against role criteria, interview transcript) and an "explainable score." This is a conversational/structured-screening layer, explicitly positioned as going beyond resume-text keyword analysis, with governance run through IBM watsonx.governance for bias monitoring/EU AI Act alignment. (Lever Blog, "Lever's Spring 2026 Release," https://www.lever.co/blog/from-chaos-to-clarity-to-connection-how-lever-s-spring-2026-release-puts-the-human-back-in-hiring)
- **Keyword search:** Lever, like Greenhouse, is fundamentally a recruiter workflow/pipeline tool; no primary source found describing a distinct "ATS score" surfaced to candidates or automatically computed pre-human-review, consistent with Greenhouse's model of Boolean search being a human-initiated action.

### Workday Recruiting

- **Skills Cloud (primary):** Workday's own blog is explicit that it is *not* keyword matching: "you shouldn't have to rely on keyword mapping. The technology should understand how skills relate to one another." Skills Cloud instead builds a "spatial representation" of skills extracted from structured/unstructured documents (including resumes) using ML, inferring related/adjacent skills rather than requiring literal term matches. (Workday Blog, "The Foundation of the Workday Skills Cloud," https://blog.workday.com/en-us/foundation-workday-skills-cloud.html)
- **Illuminate / HiredScore (primary launch facts, secondary analysis of mechanics):** Workday announced "Illuminate," its next-generation AI layer, on 2024-09-17, including a Recruiting Agent for sourcing/screening (available first via HiredScore, more deeply integrated into core Workday from spring 2025). (Workday Newsroom, "Announcing Workday Illuminate," https://newsroom.workday.com/2024-09-17-Announcing-Workday-Illuminate-TM-The-Next-Generation-of-Workday-AI) Workday acquired HiredScore in 2024; industry analyst Josh Bersin (a first-party HR-tech research org, used here since Workday hasn't published a plain-language technical explainer of matching internals) frames the shift as: "The original idea of a resume parser (software that reads a resume and scores it against a job description) has evolved into complex text analysis and AI-powered inference technology," and that with HiredScore "Workday's ATS now benefits from a first class matching and candidate scoring solution" it lacked before, because matching "dozens of complex relationships" (skills, credentials, industry experience, likely fit) is "a sophisticated problem" that plain keyword search doesn't solve well. (Josh Bersin, "Workday To Acquire HiredScore, A Potential Shakeup In HR Technology," https://joshbersin.com/2024/03/workday-to-acquire-hiredscore-a-potential-shakeup-in-hr-technology/) — Bersin's characterization that pre-acquisition Workday matching was "limited" is analyst opinion, not a Workday admission, but is consistent with Workday's own framing that Illuminate/HiredScore is a step-change.
- **Parsing/format limitations:** No Workday-published (support.workday.com is behind customer login and was not accessible) primary documentation of parsing failure modes was found. Widely repeated claims about multi-column layouts, merged table cells, text boxes, and header/footer contact info breaking Workday parsing come from third-party "beat the ATS" content sites (e.g. Resume Optimizer Pro) and **should be treated as unverified vendor-marketing-adjacent claims**, not confirmed Workday behavior — though they are directionally consistent with Greenhouse's own documented parsing failure modes (which cover the same categories: images, tables, headers/footers, multi-column).
- **Parsing engine/partner:** Not disclosed in any primary source found.

### Teamtailor

- **Resume Parser (primary):** Teamtailor's own product page states its Resume Parser "automatically fill[s] in the basic data from their CV" — specifically **name, email, phone number, and LinkedIn URL** — and attaches the CV file to the new candidate record. Users review parsed fields before confirming, up to 100 candidates at a time via drag-and-drop. No mention of skills, work history, or education extraction in the primary product materials found — this is a much thinner field set than Greenhouse's or Workday's claimed extraction. (Teamtailor Product News, "Auto-add candidate information with Resume Parser," https://www.teamtailor.com/en/productnews/auto-add-candidate-information-with-resume-parser/)
- **AI "Co-pilot" resume summaries (primary):** A separate AI feature auto-generates a five-point bullet summary of a candidate's most recently uploaded resume for faster recruiter screening, and explicitly strips identifying details (name, email, gender, etc.) from the summary shown, presumably for bias-mitigation purposes. The underlying model/technique (keyword vs. LLM) is not disclosed. (Teamtailor Support Center, "Co-pilot: Resume summaries," https://support.teamtailor.com/en/articles/8403177-co-pilot-resume-summaries)
- **API (primary):** Candidate API objects include first-name, last-name, email, phone, linkedin-url fields and a resume/upload relationship — consistent with the thin structured-field set the product page describes. No public "match score" or parsed-skills endpoint found. (Teamtailor API docs referenced via Teamtailor Support Center, "Self-Import via API," https://support.teamtailor.com/en/articles/8890189-self-import-via-api)
- **Parsing engine/partner:** Not disclosed in any primary source found.

## 3. General recruiter / keyword-screening evidence

- **The specific "keyword-stuffing beats the ATS" narrative is not supported by evidence and traces to unverifiable marketing.** An investigation into the widely repeated "75% of resumes are auto-rejected by ATS" statistic traced it to marketing claims by Preptel, a resume-software vendor that shut down in 2013 without ever publishing a methodology, dataset, or study — "there was never an original to pin it to," which is why the number drifts between 70/75/88% across sources. The same investigation directly rebuts a common "beat the ATS" tactic: hiding keywords in white text "does not sneak you past the machine. An ATS strips formatting and reads the underlying text, so hidden words are ingested as plain text and appear in the parsed output the recruiter reads" — and can be flagged as manipulation. (Uncharted Career, "The '75% of resumes are auto-rejected' myth, traced to its source," https://unchartedcareer.com/blog/the-75-of-resumes-are-auto-rejected-myth-traced-to-its-source — this is investigative/secondary reporting, not a vendor primary source, but it is sourcing-critical in exactly the way the vendor marketing it debunks is not, and no better primary source addresses this specific myth.)
- **Rigid keyword/credential filtering is a well-documented real problem — but the harm runs the opposite direction from what `ats_lint.py` optimizes for.** Harvard Business School (Fuller & Raman) with Accenture surveyed 8,000+ "hidden" workers and 2,250+ executives across the US/UK/Germany: 88% of employers agreed qualified candidates are screened out because they don't match exact ATS filter criteria; the most common automated filters are employment-gap screens (>50% of companies), then skills keywords, education credentials, and job-title matches. (Harvard Business School / Accenture, "Hidden Workers: Untapped Talent," summarized via HBS Working Knowledge, https://www.library.hbs.edu/working-knowledge/how-to-tap-the-talent-automated-hr-platforms-miss) Peter Cappelli (Wharton) makes the same point in Harvard Business Review: companies "piled on job requirements, baked them into the applicant-tracking software that sorted résumés according to binary decisions (yes, it has the key word; no, it doesn't), and then found that virtually no applicants met all the criteria." (Cappelli, "Your Approach to Hiring Is All Wrong," HBR, May-June 2019, https://hbr.org/2019/05/your-approach-to-hiring-is-all-wrong) **This is evidence that rigid keyword requirements over-reject good candidates — it is not evidence that maximizing keyword coverage on a candidate's own CV meaningfully improves pass-through odds through a given company's specific, unknown filter configuration.**
- **Recruiters do scan for keywords under time pressure, but spend most attention on structured fields (title, dates, employer, education), not free-text density.** TheLadders' 2018 eye-tracking study (an original study conducted by a job-matching/career-services company — a first-party but not fully independent source) found recruiters spend on average 7.4 seconds on initial resume review (up from 6 seconds in a 2012 predecessor study), and that a large share of that attention goes to name, current/previous titles, employment dates, and education rather than reading prose bullet-by-bullet. (TheLadders, "Eye-Tracking Study, 2018," https://www.theladders.com/static/images/basicSite/pdfs/TheLadders-EyeTracking-StudyC2.pdf) A SHRM Talent Trends article quotes an HR-tech commentator acknowledging the same dynamic for pre-AI human screening: "When a recruiter has 200 resumes on their desk, they are not looking at all 200 resumes. They are scanning each resume for key words" — but frames this as itself a bias-prone shortcut, not a validated evaluation method, and cites data that "19% of organizations that use automation or AI in hiring report that their tools have overlooked or screened out qualified applicants." (SHRM, "Recruitment Is Broken. Automation and Algorithms Can't Fix It.," https://www.shrm.org/topics-tools/news/hr-trends/recruitment-is-broken)
- **AI screening adoption is real and growing, and vendors describe it as explicitly moving away from flat keyword matching.** SHRM's 2025 Talent Trends research states 44% of organizations use AI for resume screening (part of 43% using AI for HR broadly, up from 26% in 2024); more current tools evaluate meaning/context rather than only exact-term matches, per SHRM's characterization: "the migration from pattern-matching models to large language model-based tools that read and interpret resume content contextually." (SHRM, "The Role of AI in HR Continues to Expand," https://www.shrm.org/topics-tools/research/2025-talent-trends/ai-in-hr) This is consistent with what Greenhouse, Lever, and Workday's own docs say about their 2025-2026 AI features (semantic/similar-keyword matching, structured screening dossiers, skills-graph inference) — none of the vendor primary sources found describe their current systems as flat substring/keyword-count matchers.
- **Quantified-metrics claims from resume-advice content are mostly unverifiable marketing and were excluded.** Widely circulated stats like "resumes with quantified achievements are 40% more likely to capture attention (Harvard Business Review)" or "2.5x more interview invitations (LinkedIn, 2023)" surfaced only on resume-optimization content-marketing sites (Resume Optimizer Pro, ResumeWorded, Vernovis, ResumeGiants, iCareerSolutions, etc.) with no locatable original HBR article or LinkedIn dataset behind them — the same pattern as the debunked "75%" ATS myth. **These specific numeric claims could not be verified against a primary source and are not cited as evidence here.** The Ladders eye-tracking study (above) is the one credible, methodologically-described (if vendor-adjacent) data point suggesting recruiters' attention gravitates to concrete, scannable information over prose — which is indirect, not direct, support for the value of quantified bullets.

## 4. Gaps — things real ATS/recruiter screening cares about that `ats_lint.py` doesn't check at all

1. **Format/structure parseability of the actual exported artifact.** Greenhouse's own troubleshooting docs list graphics/photos/word art, image-uploads, multi-column layouts, tables, and header/footer-placed contact info as documented causes of failed parsing. `ats_lint.py` operates purely on the author's markdown source and never touches the rendered PDF/DOCX the CV pipeline exports or that any real ATS ingests — it cannot detect any of these failure modes because it never sees the artifact that would exhibit them. This is the single largest structural gap between the tool and reality.
2. **Contact-field / work-history / education extraction correctness.** Every platform researched (Greenhouse, Lever via Sovren-if-true, Workday, Teamtailor) extracts structured fields — name, email, phone, LinkedIn, employer, dates, degree — into a candidate record that recruiters see and search on independent of resume prose. `ats_lint.py` has no notion of these fields at all, so it cannot flag a CV where, e.g., dates are in a format that would fail to parse, or contact info sits in a header (which Greenhouse explicitly warns is stripped).
3. **Structured-field/Boolean recruiter search behavior.** Greenhouse's actual recruiter-facing search is a human-triggered Boolean query (AND/OR/NOT, phrase, wildcard-stemming) over resumes+notes+scorecards together, not an automatic per-applicant score. `ats_lint.py`'s framing — a single coverage percentage against 22 auto-extracted JD terms — has no analog to how a recruiter would actually construct and run a search, and doesn't model wildcard stemming, phrase matching, or the fact that notes/scorecards (not just the resume) are searched.
4. **Semantic/skills-taxonomy matching now used by every vendor researched.** Workday's Skills Cloud explicitly rejects "keyword mapping" in favor of an ML-derived skills graph with 200,000+ canonical skills and inferred relationships (e.g., Excel → data analysis). Greenhouse's Talent Matching surfaces "matched and similar keywords." Lever's AI Screening by VONQ produces a "Candidate Dossier" from a structured interaction, not resume text matching. `ats_lint.py`'s variant-generation (plural/singular, split on `/`/`-`, a nine-entry EN/SV translation dict) is a much narrower, brittle proxy for what these systems now claim to do.
5. **Whitelist/stopword maintenance burden and false negatives it implies.** The `TECHNICAL_TERMS` whitelist (~35 terms) and stopword lists are hand-maintained and English/Swedish-only; any JD using a technology or domain term outside that list only ranks by frequency among non-technical-signal terms, and any true technical term missing from the whitelist (e.g., a newer framework, a non-tech-but-role-critical term) gets deprioritized in the top-22 selection — a maintenance liability with no analog in vendor systems, which use externally maintained skills ontologies (Workday's 200k-node graph) rather than a hardcoded list.
6. **No handling of the "requirements maximalism causes false rejection" problem documented by Cappelli/HBS.** The tool's incentive structure (raise coverage% by adding more JD-term matches to the CV) pushes in the opposite direction from what the HBS "Hidden Workers" research flags as the actual failure mode in the market — over-specified, rigid keyword requirements causing real ATSes to over-reject qualified people. `ats_lint.py` doesn't and can't address this because it has no visibility into how any given company's actual filter is configured; it only sees the JD text.

## 5. False confidence — things `ats_lint.py` measures and scores, where the score doesn't predict what it implies

1. **"Coverage % via substring match on markdown source" does not meaningfully predict "will pass a Greenhouse/Lever/Workday/Teamtailor screen."** None of the four platforms researched are shown, in any primary source found, to compute or gate on a flat percentage-of-JD-terms-present score against free text. Greenhouse's automated ranking (Talent Matching) is opt-in, calibration-based, semantic, and explicitly non-gating ("does not automatically advance or reject"). Lever's automated layer (AI Screening by VONQ) scores a structured interview interaction, not resume-text overlap. Workday explicitly says it avoids "keyword mapping." Teamtailor's documented parser doesn't even extract skills/keywords, only contact fields. **The tool's coverage percentage and STRONG/OK/WEAK verdict imply a pass/fail prediction the evidence does not support for any researched platform.**
2. **Substring matching on the author's own markdown, rather than the exported file, cannot represent whether "the term is present in what the ATS/recruiter will actually see."** Even if a real ATS did do flat keyword matching on ingested text, the parse quality depends entirely on the exported artifact's structure (per Greenhouse's documented failure modes), which `ats_lint.py` never inspects. A CV can score 100% coverage in the tool and still fail to parse at all if the exported PDF uses a two-column layout — the tool has zero signal on this axis.
3. **The 22-term JD-term cutoff and technical/frequency ranking is an internal heuristic with no external validation against how any real system selects "important" terms.** Greenhouse's Talent Matching uses recruiter-defined *weighted* calibration criteria (the recruiter decides what matters and how much); Workday's Skills Cloud uses a skills graph with inferred relationships; neither ranks by "hardcoded technical whitelist, then raw frequency" the way `ats_lint.py` does. There's no evidence this particular ranking method approximates what any real system or human recruiter would consider "key terms" for a given JD.
4. **"Single-section" flag (present in fewer than 2 sections) has no documented analog in how recruiters or ATS UIs weight term placement** (e.g., no source found suggesting Greenhouse's or Workday's ranking gives extra credit for a term appearing in a Skills section vs. a Summary section vs. Experience). This heuristic may be reasonable CV-craft advice on its own terms but isn't evidenced as correlating with ATS/recruiter outcomes specifically.

## 6. What's actually well-supported

1. **Keyword presence in general (not stuffing, but genuine topical/skill overlap with the JD) is a reasonable thing to check.** Multiple sources — Cappelli/HBR, the HBS Hidden Workers research, SHRM — describe real hiring systems (both AI and human) as fundamentally keyword/skill/title-driven at some layer, even as they critique over-rigid keyword gating. Checking whether a CV plausibly covers the JD's stated skills and responsibilities is directionally sound craft advice, independent of whether it predicts passing any specific vendor's algorithm.
2. **Warning about missing terms so the author can add them "if truthful" is a defensible design choice**, given the well-documented HBS/Cappelli finding that companies do build rigid keyword/title/credential filters and do reject qualified candidates who describe the same skills in different words — genuinely having the skill and simply not naming it the way the JD does is a real, evidenced failure mode this heuristic targets correctly, even though the tool can't know if a given target company's filter is that rigid.
3. **The quantified-metrics count (regex for `%`, `x`, currency, or any number) is a defensible, if blunt, proxy.** While the specific "40% more likely to be read" / "2.5x more interviews" statistics circulating online could not be verified to a primary source and are excluded from this report, the more conservative and better-supported finding — from TheLadders' original eye-tracking research — is that recruiters' scarce attention (~7.4 seconds) gravitates to concrete, scannable, structured information (titles, dates, employer names) over unstructured prose. Numbers and metrics are exactly the kind of scannable, concrete signal that finding favors, even though the eye-tracking study itself doesn't isolate "numeric metrics" as its own variable.
4. **Word count / length targeting is uncontroversial and consistent with the same attention-scarcity evidence** (short review time favors concision), though no source specifically validates the tool's 430-560 word target as opposed to any other range in that neighborhood.
5. **Treating the tool as a pre-submission "did I forget an obviously relevant skill/keyword" sanity check for the author — not a pass/fail ATS predictor — matches how the vendors themselves position analogous features.** Every AI-matching feature found in vendor primary sources (Greenhouse Talent Matching, Teamtailor Co-pilot summaries) is explicitly framed as assistive to a human recruiter, not a determinative gate — which is a reasonable posture for `ats_lint.py` to adopt for itself, and arguably already implicit in it being a linter run before finalization rather than a hard gate.
